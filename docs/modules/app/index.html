Qt Application#

The Qt application provides the graphical user interface and runtime infrastructure of Fluvel Set.

It is responsible for user interaction, session management, camera and image workflows, and integration with the underlying Fluvel IP image processing library.

The application is organized into four main areas:

  • UI: windows, dialogs and reusable user interface components.

  • Application Core: controllers, settings management and execution workflows.

  • Media: video export infrastructure and media backend integrations.

  • Interoperability: adapters and integration layers connecting the application to external libraries and processing backends.

Architecture#

Fluvel Set follows a mixed MVC/MVP architecture. The controllers drive the session (sources, threads, workers, settings) and also play the role of presenter: they turn the results of the algorithm into what the view displays. The view is passive and the windows only connect the components together. The algorithm itself, in Fluvel IP, does not depend on Qt.

Threads and data flow#

Every long computation of the application runs outside the GUI thread, and every thread follows the same producer/consumer scheme: a producer hands data to a consumer that lives in another thread, and the two never wait for each other, except where this is wanted. What changes from one case to another is the answer to a single question: what happens when the consumer is slower than the producer? The data can be dropped, the producer can wait, or the data can be stored.

Case

Producer -> consumer

If the consumer is slower

Video session

video source -> processing thread

Drop: only the latest frame is kept, the older ones are lost, so the latency stays bounded.

Image session

worker -> display

Wait: the worker does not compute a new frame until the controller has acknowledged the previous one (back-pressure).

Settings preview and analysis

window -> worker

Latest wins: only the latest request is computed. Each request has a number, and an answer that no longer matches the last request is ignored.

Recording

GUI thread -> encoder thread

Store: the buffer keeps the frames in memory and spills them to disk when its limit is reached, so no frame is lost.

Snapshot

GUI thread -> writer thread

Bounded queue: the files are written one at a time, in order.

The sections below detail each case. In all of them, the data crosses the thread boundary either by a queued signal (the value is copied or shared as read-only), or by a small structure protected by a mutex.

Video session#

Commands go from the window to the algorithm. Frames go the other way: the video source delivers a frame, the processing thread keeps only the latest one, runs the filters and the active contour within a time budget, and the controller prepares the display data for the viewer.

The colored frames show where each component runs. The interface, the controller and the viewer live in the GUI thread. The video source belongs to the Qt Multimedia backend, which delivers frames from its own threads. The processing thread runs the algorithm. A dashed arrow that crosses a frame is a signal delivered across threads: the receiver handles it later, in its own thread.

Image session#

The image worker lives in its own thread. The controller only posts commands to it, so the interface never waits for the filters or for the contour iterations. In interactive mode the worker is paced by the clock: every 16 ms (about 60 frames per second, computation included) it computes 10 iterations and publishes the contour, so the evolution stays visible even on small images that would converge in a few milliseconds. It never computes ahead of the display: the controller acknowledges each frame it has consumed. When one iteration takes longer than a frame, the worker simply runs as fast as it can. In converge mode the worker runs at full speed, without pacing, and publishes only the final result. When a new image is loaded, the image without filters is displayed until the worker returns the processed one. Each initialization has a number, and an image that belongs to an older one, still on its way, is ignored, so it can never replace the current image.

Settings preview#

The settings dialog shows a preview of the image after the downscale and the filters. Computing it can take a while on a large image, so the controller does not do it itself: it sends a numbered request to a preview worker that lives in its own thread, and the dialog shows that the result is awaited. If several requests arrive while one is running (for example while a slider is dragged), only the latest is computed. The worker answers with the images and the duration of the filters, and the controller ignores an answer that is already outdated. Editing the initial shape needs no computation of this kind and stays in the GUI thread. When a new image arrives, it is shown without filters until its first preview is ready, instead of the previous image.

Analysis#

The analysis window compares two shapes (intersection, Hausdorff distance, quantile and distance between centroids). The measures can take a long time on large shapes, so they are computed by an analysis worker in its own thread: the window copies the shapes, the images and the options into a request, and the button stays disabled until the answer arrives. As for the preview, only the latest request is computed and a result that no longer matches the selection is ignored. The worker returns the statistics as a shared read-only object, so changing the percentile only reads the quantile from it, without any new computation.

Recording#

Recording is handled by the capture controller, independently of the video session: it only receives the frames that the window gives it, so it can be reused with other sources. The window draws the contour layers on the displayed image before submitting it, so the recorded video shows what the user sees.

The frames go through a buffer protected by a mutex: the GUI thread pushes them and a dedicated recorder thread pops and encodes them with FFmpeg. The buffer keeps frames in memory and spills them to disk when its limit is reached. When the recording stops, the recorder thread first drains the buffer, then closes the file and, if requested, converts the segments to standard MP4. Its signals reach the controller in the GUI thread.

Snapshot#

A snapshot is simpler. The window copies the displayed image, draws the contour layers on the copy and gives it to the capture controller. The controller puts it in a small bounded queue, and a dedicated thread writes the files one at a time, so saving never blocks the interface. The result, a file name or an error, comes back to the controller and is shown to the user.

Configuration#

Settings do not follow the data path. They are stored in the ApplicationSettings singleton, which emits a signal when they change, and three listeners react independently:

  • the controller forwards the processing settings to the thread or worker (they are applied from the next frame) and restyles the current layers, so a display change is visible immediately, even when the video is paused;

  • the window applies the view settings (mirror, smoothing, minimap, overlay) directly to the viewer, without going through the controller;

  • the window also refreshes its own widgets;

  • the capture controller keeps its own copy of the snapshot and recording preferences. It never reads the singleton: the window gives it the values at start-up and whenever they change, and each snapshot request carries a copy of them.

The controllers do not know the singleton either. It is the window that connects its signals to their slots, so a controller can be used with any source of settings.

Settings dialogs#

The session dialogs (image and video) never read or write the singleton. A dialog receives its configuration once, when it is created, and keeps two copies: the committed one, which is what the application uses, and the edited one, which follows the widgets while the dialog is open.

  • OK copies the edited configuration to the committed one and emits a signal. The window connects that signal to the setter of ApplicationSettings, which then notifies the controllers.

  • Cancel restores the edited configuration from the committed one and refreshes every widget, so the dialog always shows the configuration that is really applied when it is opened again.

The dialog keeps its own copy, and nothing refreshes it afterwards. This is correct as long as the dialog is the only code that changes these settings, which is the case today: the only writers of the session settings are the two windows, and each of them only forwards the signal of its own dialog. If a new path starts to modify them (loading a preset, resetting the settings, another window), the owner of the dialog must give it the new configuration, otherwise the dialog would show and later commit a stale copy.

The preferences dialog (language, snapshots, video recording, recording buffer) follows the same user-visible behavior, with a different mechanism. It is a single global dialog with no owning window to relay its values, so it reads and writes ApplicationSettings itself.

  • Opening the dialog reloads every widget from the application settings, so it always shows what is really applied. Opening it again while it is already visible keeps the pending edits.

  • OK writes the values to the singleton, which notifies the windows, and saves them to disk.

  • Cancel (or closing the window) writes nothing. The edits are discarded by the reload of the next opening.

  • Restore Defaults fills the widgets with the factory values, like the same button of the session dialogs. Nothing is applied until OK, and Cancel discards it. The default folders depend on the platform (standard pictures and movies locations given by Qt), so they come from ApplicationSettings::defaultSnapshotPreferences() and defaultVideoRecordingPreferences(), which the loading of the settings also uses. The language goes back to System, which, as any language change, takes effect after a restart.

Reloading at each opening replaces the committed/edited copies: there is no second copy that could become stale, so the limit described above does not apply to this dialog.
